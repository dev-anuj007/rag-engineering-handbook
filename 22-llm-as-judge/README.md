# 22 LLM-as-a-Judge

## Objective

Design rigorous, automated LLM evaluation pipelines using structured Likert rubrics, G-Eval framework techniques, pairwise battle comparisons, and position-bias mitigation.

## Why It Matters

Human evaluation does not scale to thousands of daily enterprise queries. High-capacity LLM judges (e.g. Gemini 2.5 Flash / Pro) correlate with human domain experts at $>85\%$ when provided with explicit step-by-step rubrics.

## Core Concepts

- **Structured Scoring Rubrics**: Explicitly defining criteria for scores 1 through 5 prevents score drift.
- **Position & Verbosity Bias**: LLMs naturally favor longer responses and options presented first; positional swapping cancels this bias.
- **Chain-of-Thought Evaluation**: Forcing the judge to output reasoning *before* emitting the numeric score improves consistency.

## Architectural Deep Dive & Mental Model

## 1. First-Principles Mechanics of LLM-as-a-Judge

LLM-as-a-Judge leverages frontier models (e.g. Gemini 1.5 Pro, GPT-4) equipped with structured evaluation rubrics and chain-of-thought (CoT) reasoning to evaluate complex qualitative dimensions: coherence, tone, groundedness, and semantic completeness.

```
                    ┌────────────────────────────────────────┐
                    │ Evaluation Input:                      │
                    │   - Query (Q), Context (C), Answer (A) │
                    └───────────────────┬────────────────────┘
                                        │
                                        ▼
                    ┌────────────────────────────────────────┐
                    │ Structured Evaluation Rubric & CoT     │
                    │   - Step 1: Extract criteria           │
                    │   - Step 2: Reason step-by-step        │
                    │   - Step 3: Assign score (1..5)        │
                    └───────────────────┬────────────────────┘
                                        │
                                        ▼
                    ┌────────────────────────────────────────┐
                    │ Bias Mitigation Layer                  │
                    │   - Position Swapping (A vs B pairwise)│
                    │   - Logit Probability Expectation      │
                    └───────────────────┬────────────────────┘
                                        │
                                        ▼
                    ┌────────────────────────────────────────┐
                    │ Calibrated Evaluation Score (0.0..1.0) │
                    └────────────────────────────────────────┘
```

## 2. Mathematical Formalization: G-Eval Framework & Probability Expectation

Standard LLM prompting asking for a discrete integer score ($s \in \{1, 2, 3, 4, 5\}$) suffers from high variance. **G-Eval (Liu et al., 2023)** computes the **mathematical expectation** over token generation probabilities:

$$\text{Score}_{\text{G-Eval}} = \sum_{k=1}^5 k \cdot P(\text{Token} = \text{"}k\text{"} \mid \text{Prompt}, \text{CoT})$$

Where $P(\text{Token} = \text{"}k\text{"})$ is extracted directly from the model's output log probabilities (top logprobs), normalized across the score token subset:

$$P(\text{Token} = \text{"}k\text{"}) = \frac{\exp(\text{logit}(k))}{\sum_{j=1}^5 \exp(\text{logit}(j))}$$

This converts discrete integer scores into smooth, continuous, highly discriminative scalar metrics.

## 3. Judge Biases & Mathematical Mitigations

| Bias Type | Manifestation | Mitigation Strategy |
|---|---|---|
| **Position Bias (Pairwise)** | Model favors Candidate A simply because it appeared first in the prompt. | **Permutation / Position Swap**: Evaluate $(A, B)$ and $(B, A)$; average or discard ties: $\text{Score} = \frac{S(A, B) + (1 - S(B, A))}{2}$. |
| **Verbosity Bias** | Model assigns higher scores to long, verbose answers regardless of conciseness. | Penalize token length in rubric; normalize score against word count. |
| **Self-Enhancement Bias** | Models favor answers generated by their own model family. | Use cross-model judges (e.g. Gemini evaluates Llama outputs). |

---

## 4. Failure Modes & Mitigations

1. **Non-Deterministic Score Variance**:
   - *Failure*: Running the judge twice with $T=0.7$ produces scores of $2/5$ and $5/5$ for the same answer.
   - *Mitigation*: Enforce $T=0.0$ greedy decoding or calculate G-Eval token logit expectations.
2. **Evaluation Cost Explosion on Large Datasets**:
   - *Failure*: Evaluating 100,000 production queries daily using frontier LLM judges incurs thousands of dollars in API bills.
   - *Mitigation*: Run LLM judges on a statistically significant random sample ($5\%$) or distill judge feedback into a small, fast local BERT classifier.

---

## 5. SOLID Principles in LLM-as-a-Judge

- **Single Responsibility (SRP)**: `RubricEngine` formats evaluation criteria; `JudgeClient` executes LLM inference; `BiasCalibrator` handles pairwise swapping.
- **Open/Closed (OCP)**: Custom evaluation rubrics implement `RubricProtocol`.
- **Liskov Substitution (LSP)**: All judges implement `JudgeProtocol`.
- **Dependency Inversion (DIP)**: Benchmark runners depend on `JudgeProtocol`.

## Strengths & Trade-offs

- **Strengths**: Automated, highly scalable, provides human-readable explanations for every score.
- **Weaknesses**: Susceptible to self-enhancement bias when evaluating models from the same family.

2. *How do you prevent 'judge hacking' where generated responses exploit the known stylistic preferences of the evaluator LLM?*
